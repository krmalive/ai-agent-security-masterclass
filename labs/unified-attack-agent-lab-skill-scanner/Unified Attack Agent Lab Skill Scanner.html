Unified Attack-Only Vulnerable Agent Lab (ASI01/ASI02/ASI03)

This lab intentionally demonstrates three OWASP Agentic vulnerabilities in one application:

  • ASI01: Agent Goal Hijack
  • ASI02: Tool Misuse & Exploitation
  • ASI03: Agent Identity & Privilege Abuse

The app is implemented with OpenAI Agents SDK and uses Requesty (openai/gpt-4.1-mini) for model routing.

Lab Goal

This lab is designed as a single storyline:

  1. Start one vulnerable multi-agent app.
  2. Manually exploit three attack paths (ASI01, ASI02, ASI03) using chat/file interaction.
  3. Scan the same skill files using skill-scanner.
  4. Compare manual exploit evidence with scanner findings.

If all steps work, the lab proves both:

  • attacks are practically exploitable in runtime behavior, and
  • risks are partially detectable from skill artifacts.

Pure Skill+LLM Guarantee

This lab runtime is designed to avoid deterministic keyword routing and canned success-path responses.
Action selection and vulnerable behavior come from:

  • planner_skill (primary decision)
  • invoice_skill (ASI01 action behavior + response shaping)
  • support_skill (ASI02 action decision + response shaping)
  • delegation_skill + finance_skill (ASI03 delegation/access chain)

The app may return explicit error messages when a skill does not produce valid JSON for required structured decisions, but it should not silently fall back to hardcoded mimic success responses.

What are the consequences of these vulnerabilities

  • Unauthorized Actions - Refunds and other sensitive operations can execute without explicit user authorization.
  • Scope Escalation - Benign requests can be transformed into high-impact tool actions.
  • Data Exposure - Unsafe tool invocation can export sensitive customer/finance data.
  • Privilege Escalation - Delegated low-privilege agents may inherit broad access and perform restricted actions.
  • Trust Violation - The system may act on hidden instructions over explicit user intent.

4) Scan with LLM (recommended semantic path)

Use this for semantic findings + optional meta filtering.

JSON report (with LLM)

skill-scanner scan-all ../skills --recursive \
  --use-llm --llm-provider openai \
  --enable-meta --llm-consensus-runs 3 \
  --policy strict \
  --format json --output-json ../reports/with-llm-scan.json
Copied!

HTML report (with LLM)

skill-scanner scan-all ../skills --recursive \

  --policy strict \
  --format html --output-html ../reports/with-llm-scan.html

CLI outcome note

When scanner commands run successfully in CLI mode, you should see:

  • A terminal summary block with:
    • Skill (or total skills scanned for scan-all)
    • Status ([OK] SAFE or [FAIL] ISSUES FOUND)
    • Max Severity
    • Total Findings
    • Findings Summary by severity
  • Output confirmation by artifact:
    • JSON file written to the --output-json path
    • HTML report written to the --output-html path
    • Markdown report written to the --output-markdown path

Note:

  • Status: [OK] SAFE means no findings were detected by enabled analyzers for that run.
  • Status: [FAIL] ISSUES FOUND means one or more findings were detected.
  • This is best-effort detection; no findings does not prove absence of risk.

How to read scanner results for this lab

  • Map findings to demo classes:
    • ASI01: prompt/instruction override, trust-boundary failures, document-driven action hints.
    • ASI02: unsafe tool invocation, exfiltration or high-risk execution patterns.
    • ASI03: over-broad delegation, inherited privilege/identity misuse patterns.
  • Prioritize HIGH/CRITICAL findings for the demo narrative.
  • Treat “No findings” as “no known patterns detected,” not proof of safety.

Mapping template (use in final report)

  • ASI01 runtime evidence -> goal_shift_detected / refund_executed_unauthorized -> scanner findings in invoice_skill / planner_skill
  • ASI02 runtime evidence -> high_risk_tool_called / data_export_generated -> scanner findings in support_skill or support helper scripts
  • ASI03 runtime evidence -> delegation_context_inherited / privileged_action_by_low_priv_agent -> scanner findings in finance_skill or delegation helper scripts

Additional mapping note for ASI03

If strict+behavioral scanning does not flag finance-skill, keep ASI03 evidence anchored in runtime telemetry and delegation trace outputs.
This is acceptable and should be documented as detection-gap vs exploitability-gap.

Conclusion

This unified app demonstrates exploitability across goal routing, tool execution, and delegated identity boundaries. Combining runtime exploit evidence with both non-LLM and LLM scanner reports provides a defensible ASI01/ASI02/ASI03 POC narrative.
